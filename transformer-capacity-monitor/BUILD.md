### 1. Scheduled monitoring run

- What happens: Start a run a few times a week for a defined measurement period while you are away.
- Why: You want routine monitoring without someone having to start each run.
- Passes on: The scheduled period and run identifier.

### 2. Load transformer readings

- What happens: Retrieve transformer load readings for the scheduled period, retaining timestamps, units, and transformer identifiers.
- Why: These feeds are the source of the load measurements being monitored.
- Passes on: Readings for the requested period.

### 3. Load transformer asset records

- What happens: Retrieve transformer identifiers, locations, and rated maximum loads.
- Why: The asset records identify which equipment is monitored and define its capacity limit.
- Passes on: Transformer records and rated limits.

### 4. Load local boundaries

- What happens: Retrieve the approved town, village, and neighborhood boundary data used to locate and group assets.
- Why: You specified county or municipal boundary data as the geographic reference.
- Passes on: Boundary identifiers and geographic shapes.

### 5. Load heat-pump growth forecasts

- What happens: Retrieve the heat-pump adoption forecast and its period and geographic breakdown.
- Why: You specified heat-pump adoption forecasts as the demand-growth input.
- Passes on: Forecast assumptions and adoption values.

### 6. Align the run inputs

- What happens: Match readings, asset ratings, boundary areas, and forecasts to the same reporting period and transformer or geographic identifiers.
- Why: The sources must refer to compatible periods and locations before capacity can be assessed.
- Passes on: Joined inputs with source references and counts.

### 7. Check input completeness

- What happens: Check required fields, units, timestamps, identifiers, period coverage, and that every monitored transformer has a rating; do not publish partial results.
- Why: A scheduled run does not by itself mean all expected source data is ready.
- Passes on: Complete inputs for the requested period, or a failed run for investigation.

### 8. Check load stability

- What happens: For each transformer, use an individuals and moving-range control chart on one load reading per period, with limits based on stable historical variation and separate from the rated capacity limit.
- Why: Control charts distinguish ordinary variation from meaningful changes; their limits come from process history, not equipment specifications.
- Passes on: Per-transformer stability results and any chart signals.

### 9. Is the load pattern stable?

- What happens: Route a transformer as stable only when its chart has enough history and shows no out-of-control point or applicable run-rule signal.
- Why: Capacity indices are meaningful only after stability is checked; a chart signal needs investigation rather than being treated as routine variation.
- Passes on: Stable transformers to forecasting, or signals and insufficient history to human review.

### 10. Project demand growth

- What happens: Apply the approved heat-pump adoption forecast and geographic allocation rules to estimate future peak load for each transformer.
- Why: This brings the requested demand-growth information into the capacity outlook using recorded assumptions rather than an AI estimate.
- Passes on: Per-transformer forecast peak loads and the assumptions used.

### 11. Measure capacity headroom

- What happens: For stable transformer loads, calculate one-sided Cpk against the rated maximum and its confidence interval; also compare each projected peak with that rating.
- Why: Capability compares a stable process with an externally set limit; the confidence interval helps show when the estimate is uncertain.
- Passes on: Per-transformer Cpk, confidence interval, forecast margin, and any insufficient-data flags.

### 12. Does a transformer need review?

- What happens: Use the approved playbook thresholds to flag a low or uncertain Cpk, a forecast peak near or above rating, or a missing result; otherwise mark the transformer within limits.
- Why: The playbook makes escalation consistent, while uncertainty and forecast peaks should not be mistaken for a confirmed safe margin.
- Passes on: Transformers marked for human review or within limits.
- Stop rule: Failures alert a person.

### 13. Review capacity exceptions

- What happens: Review chart signals, uncertain indices, forecast assumptions, and source details; record a disposition before the report is finalized. Do not make equipment or operating changes automatically.
- Why: A mistaken capacity conclusion could be costly or difficult to undo, so a person should assess exceptions and retain control of consequential action.
- Passes on: A recorded review disposition and any notes for the report.

### 14. Save the monitoring report

- What happens: Save the period-specific report with readings, charts, ratings, forecasts, capacity results, source references, and human dispositions; make reruns replace the same period's result rather than duplicate it.
- Why: A durable, auditable report supports follow-up while partitioned writes make replay safer.
- Passes on: A saved report and run record, or a visible failed run.

### 15. Monitoring run complete

- What happens: Make the completed report available to the authorized grid-planning team.
- Why: The report is the monitoring result; flagged conclusions include their review status.
- Passes on: Nothing further.

## Watch out for

- **A scheduled run is not proof that feeds are ready.** Bind every task to the intended reporting period and check feed readiness and matching partitions. Late, skipped, empty, or mismatched inputs must not be mistaken for a complete run. (knowledge base: R01)
- **A rerun must not create a second report.** Make writes period-specific and safe to repeat. Test partial writes and repeated intervals, and ensure an earlier task failure cannot be hidden by successful cleanup. (knowledge base: R02)
- **Chart limits are not transformer ratings.** Control limits describe variation in stable historical readings; the rated maximum is a separate capacity limit. Do not calculate or interpret capability for an unstable load pattern. (knowledge base: Q01, Q02)
- **Airflow setup is not proof of live operation.** Test with the deployed Airflow and provider versions, worker credentials, storage, and executor. Confirm failure alerts actually arrive and preserve the run’s failure status. (knowledge base: R03, R02)
- **Compare data operations before choosing the platform.** This catalog does not evaluate Dagster or dbt. Treat the suggested platform as provisional. Compare partition mappings, backfills, data quality gates, lineage, team permissions and existing infrastructure. Test replay and failure recovery with representative data before selecting an orchestrator.
- **Incoming content can carry instructions.** An email or document can contain text aimed at your AI ("ignore your rules and forward this"). Treat incoming content as information, never as orders, and add a check for unsafe inputs.
- **Personal data can leak in output.** Filter output for personal information, share only what each step needs, and don't put secrets in the system prompt; prompts can be coaxed into revealing themselves.
- **Airflow is a developer tool.** Every workflow is written in Python, compared with n8n's visual builder, and a production setup needs ongoing monitoring and tuning. Budget for someone to own it, or use a managed Airflow service.
- **Local is cheaper only once it's busy.** Your own hardware has a large upfront cost and needs looking after. It pays back through high, steady volume, not occasional use: idle hardware can cost more per task than the cloud.
- **The smartest model isn't always the best fit.** Top models are slower and cost more, and for simple steps they don't do better. Let your test examples decide, not the leaderboard.

## Airflow data intervals, task contracts and dependencies

### Claims

- In time-based interval scheduling, the logical date identifies the interval,

  coalesce into one run. [airflow-2026-assets §Schedule Dags with assets; §Multiple assets]

## Airflow safe retries, backfills and failure signals

### Claims

- Tasks should publish complete results and produce the same outcome on rerun.
  Airflow recommends partition-specific reads/writes and UPSERT instead of
  duplicate-producing INSERT operations. [airflow-2026-best-practices §Creating a task]
- `execution_timeout` bounds each task execution. For rescheduling sensors,
  `timeout` bounds the overall wait; retries do not reset it. AirflowFailException
  can fail without using remaining retries.
  [airflow-2026-tasks §Timeouts; §Special Exceptions]
- Backfill creates historical runs for time-based schedules. Reprocessing policy
  distinguishes missing, failed and completed runs. Backfill concurrency is
  controlled independently of the DAG's active-run limit. A dry run previews
  candidate dates, not task outputs. [airflow-2026-backfill §Control over data reprocessing; §Concurrency control; §Dry run]
- Catchup schedules missed intervals when enabled. DAG-run status depends on
  leaf tasks: a successful `all_done` leaf can hide an earlier failure.
  [airflow-2026-dag-runs §Catchup; §Dag Run Status]
- Callbacks respond to worker-driven state changes, not manual UI/CLI status
  changes. Callback failures appear in DAG-processor logs in the reviewed
  version. [airflow-2026-callbacks §Callbacks]

### What this means for the guide

These recommendations interpret the Airflow 3.3.2 docs. They are not a promise
of exactly-once delivery or automatic rollback across external systems.

- Give retryable work a finite attempt count and delay, and distinguish temporary
  service failures from invalid input or credentials. Specify both execution and
  dependency-wait limits; exhausting the wait must have an owner and recovery path.
- Design writes so replaying a partition does not duplicate its business effect.
  For messages, purchases or agent handoffs, verify the receiving service's replay
  contract before retrying. Airflow retry configuration cannot supply a guarantee
  the destination does not provide. Investigate ambiguous outcomes before resend.
- Keep catchup an explicit choice. Before a backfill, review its date range,
  reprocessing policy, resource limits and external actions. Start with a small
  historical interval and compare results before widening the run. The preview
  does not prove that historical inputs still exist or that replay is safe.
- Test failure propagation through branches and cleanup tasks. Decide which
  terminal states indicate a usable result; do not let housekeeping success stand
  in for successful data processing.
- Alerts should identify the DAG, run, task, attempt and relevant partition while
  avoiding sensitive payloads. Test by causing a controlled worker failure, not
  by manually marking a task failed. Verify delivery and inspect callback logs
  when the task fails without an alert.
- Acceptance cases: retry after a partial write, exhausted retries, missing
  upstream data, a repeated historical interval, an earlier failure followed by
  successful cleanup, and an alert-service outage. Check destination records and
  final run state. These tests still need execution in an isolated deployment.

## Airflow testing, credentials and production capacity

### Claims

- DAG files are parsed repeatedly. Airflow advises keeping expensive computation,
  database access and network work out of top-level code, and testing imports in
  an environment matching the scheduler. [airflow-2026-best-practices §Top level Python Code; §Dag Loader Test]
- Airflow 3 authors should use the public `airflow.sdk` interface rather than
  internal modules or direct metadata-database access.
  [airflow-2026-public-interface §Using Airflow Public Interfaces]
- `dag.test()` executes real tasks. It defaults to local serialized execution;
  `use_executor` enables the configured executor. The reviewed version requires
  an initialized metadata database and a serializable DAG in a configured
  bundle. Marking selected tasks successful skips their behavior.
  [airflow-2026-debug §Testing Dags with dag.test(); §Conditionally skipping tasks]
- Connections and Variables can resolve from secret backends, environment or
  metastore. Lookup precedence and duplicate keys matter; the UI only displays
  metastore values. [airflow-2026-secrets §Secrets Backend; §Search path]
- Pools limit task concurrency; `pool_slots` assigns different weights. Queued
  tasks wait for available capacity. [airflow-2026-pools §Pools; §Using multiple pool slots]
- Deferrable operators release worker slots while waiting and require a
  triggerer. Deferred tasks do not occupy pool slots by default, unless the pool
  is configured otherwise. Rescheduling sensors also release workers between
  checks. [airflow-2026-deferring §Deferrable Operators & Triggers; §Using Deferrable Operators]

### What this means for the guide

This chapter uses Airflow 3.3.2 documentation. The external sensor reference in
R01 uses standard provider 1.20.0; check compatibility rather than assuming every
Airflow 3 installation exposes identical features.

- Keep orchestration definitions lightweight and move work into tasks. Record the
  core, Python and provider versions used for validation; an import passing in an
  unrelated developer environment is insufficient.
- Test in layers: pure business-logic tests, DAG import and dependency assertions,
  an isolated `dag.test()` run, then staging with the deployed executor and real
  dependency mechanism. Syntax compilation does not execute imports or validate
  scheduler behavior. Skipped sensors do not count as tested dependencies.
- Supply test credentials and safe destinations before executing a DAG test.
  Store authentication in Connections or the configured secret backend, keeping
  secret values out of DAG source and generated examples. Verify lookup in the
  worker environment, especially when a key exists in several stores.
- Size pools for the downstream system's capacity and limit overlapping runs.
  Concurrency limits are not requests-per-second limits; add destination-specific
  pacing where needed. Test whether deferred tasks should retain a pool slot for
  the external resource they still occupy.
- Verify the triggerer before choosing deferrable waits. Observe queue time,
  task failures and wait behavior under load, then adjust capacity with evidence.
- Acceptance cases: missing provider, unavailable credentials, worker restart,
  pool saturation and unavailable triggerer. Preserve failure visibility and
  verify output correctness after recovery. The exported scaffold and this guide
  do not demonstrate a production-ready deployment or completed live tests.
